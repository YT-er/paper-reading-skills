# 论文阅读方法

## 原则

- 只定义分析顺序，不预置论文内容。
- 所有判断必须来自当次材料。
- 不做逐篇摘要，不按年份机械排序。
- 生命科学材料先识别研究对象、数据/实验类型和论文类型，再选择对应阅读视角。

## 分析链

```text
目的
  -> 主体
    -> 旧瓶颈
      -> 关键动作
        -> 机制链
          -> 证据链
            -> 技术债 / 边界
```

先回答：

1. 研究目的：这项工作要把什么瓶颈、成本或能力缺口，变成什么可用收益？
2. 阅读主体：本次真正要解释的是论文、机制、系统、模型家族、数据集、benchmark，还是一个技术瓶颈？
3. 生命科学对象：研究对象是人群、疾病、组织、细胞类型、模式生物、微生物、蛋白、通路，还是数据资源？
4. 研究类型：它更像机制发现、组学分析、算法/软件/流程、临床转化、数据资源，还是治疗/诊断策略？
5. 旧瓶颈：它出现前为什么做不到？
6. 关键动作：它到底改了什么？
7. 证据边界：哪些来自论文、哪些来自 repo、哪些只是推断？

## 输出结构

```text
目的与核心结论
旧世界为什么不够
关键动作
机制链
证据链
技术债
边界
```

生命科学论文可以在正文中显式加入：

```text
研究系统与问题定义
数据 / 实验 / 队列
方法或机制链
证据质量
复现性与转化风险
```

## 生命科学通用框架

每篇生命科学材料先建立一层通用读法：

- 研究系统：人群、疾病、组织、细胞类型、模式生物、微生物、蛋白、通路或数据资源分别是什么。
- 数据与实验：WES、WGS、RNA-seq、scRNA-seq、spatial、proteomics、MS、CRISPR screen、flow、IHC、临床队列或其他实验各承担什么证据角色。
- 关键变量：基因、突变、表达、细胞状态、通路、药物、表型、临床结局或算法评分分别怎样进入结论。
- 证据强度：发现队列、验证队列、功能实验、动物模型、临床数据是否互相支持。
- 因果边界：结论是机制因果、统计相关、预测关联，还是仅提出可检验假设。
- 复现条件：需要哪些数据、代码、流程、参数、样本信息和实验条件才能复现。

## 按类型选择阅读视角

不要把所有生命科学论文套成同一模板；先判断类型，再选择必要视角。

### 组学 / 生信数据分析

- 样本量、队列来源、病例对照定义和批次效应是否支撑结论。
- QC、过滤、归一化、统计模型和多重检验是否说清楚。
- 是否有外部验证集或正交实验验证。
- 数据、代码和关键参数是否开放。

### 算法 / 软件 / 流程

- 输入、输出、核心算法、流程步骤和失败条件是什么。
- benchmark 是否公平，对照工具、版本、参数和数据拆分是否一致。
- 是否存在数据泄漏、过拟合或只在单一数据集有效的问题。
- 运行时间、资源消耗、依赖环境、Docker/Conda/Snakemake/Nextflow 支持是否足够落地。

### 机制生物学

- 核心假设、关键扰动和 readout 分别是什么。
- knockdown、overexpression、inhibitor、rescue、正交验证是否能支撑因果链。
- 细胞模型、动物模型和人类样本之间是否存在外推过度。
- 机制图要区分已证明环节和作者推断环节。

### 临床转化

- 队列设计、入排标准、终点、随访和混杂因素是否清楚。
- biomarker cutoff、风险分层或预测模型是否有独立验证。
- 临床使用场景、失败风险、成本和可解释性是否明确。
- 结论是探索性、回顾性验证，还是接近前瞻性证据。

### 免疫 / 肿瘤 / 新生抗原

- 区分 HLA typing、binding affinity、presentation、expression、clonality 和 immunogenicity 各自证据。
- 明确 SNV、indel、fusion、splicing、ERV 或 noncoding-derived antigen 的来源和过滤逻辑。
- 检查 tumor purity、VAF、CNV、RNA expression、克隆性和 MS/T cell validation 是否纳入。
- 工具或模型输出要落到候选抗原排序、患者报告、实验验证或临床决策的哪一步。

## 开头组织

生成文档式长文或 HTML 时，开头使用：

```text
研究目的
  -> 开篇总览图
    -> 核心结论
```

- 研究目的先回答“对象 / 瓶颈 / 收益”。
- 开篇总览图用 SVG 或可视化结构图压缩全文读法，帮助读者先获得大概内容。
- 总览图不是目录，不重复章节名；只放当前材料抽出的场景压力、旧瓶颈、关键动作、证据方向或结论落点。
- 核心结论再展开成完整判断，承接总览图进入正文。

## 公式处理

遇到核心公式时，不要只把公式塞进普通段落。按“教科书式解释”展开：

```text
公式回答什么问题
  -> 每个符号分别代表什么
    -> 分子 / 分母 / 约束条件的直觉
      -> 这个公式为什么导向论文的关键动作
```

- 先说明公式在算什么，不先堆符号。
- 逐项解释变量，尤其说明“越大越好 / 越小越好 / 只是中间成本”。
- 把公式连接回论文目的和机制链，避免变成孤立数学说明。
- 只解释当次材料里真正支撑结论的公式；次要公式可以保留为普通行内说明。

## 概念分段

概念底座要按“一个概念一段或一小节”组织，不把多个陌生词、机制约束和结论塞进同一段。

- 先定义概念，再讲它解决什么问题，再讲它和下一概念的关系。
- 如果同一段出现多个关键术语，优先拆成多个小标题或短段。
- 英文术语第一次作为重点出现时，附“英译中 / 怎么理解”，把字面翻译转成可操作含义。
- 抽象机制需要图解时，用小型 SVG 表达动作链或取舍关系，不只用文字解释。
- 划线解释只补读者缺口，不重复正文已有定义。
- 一个标记回答只解释当前标记，不顺手解释整条机制链。

## SVG 图解触发

稍微复杂的内容默认用 SVG 图解，不等用户明确要求“作图”。复杂度判断：

- 需要解释 3 个以上步骤、角色、模块或变量。
- 有“先后顺序、前置条件、失败链、取舍关系、预算分配、调度决策”。
- 同一段里出现多个技术对象并需要比较。
- 公式背后有分子 / 分母 / 约束 / 优化目标。
- 只用文字解释会超过 2 个自然段，或读者需要在脑中拼流程。

SVG 图解只画必要结构：

```text
输入 / 前提
  -> 关键动作
    -> 中间约束
      -> 输出 / 结果
```

- 图后必须写“这张图怎么读”。
- 图是正文解释的一部分，不是装饰。
- 图内文字短，不把长段解释塞进 SVG。
- 能用动作链表达时优先画动作链；能用对照表达时画左右对照；能用公式表达时画变量关系。

## 自检

- 开头没有研究目的，重写。
- 文档式 HTML 开头没有总览图，且读者需要先建立全局理解，补一张开篇总览图。
- 核心公式没有独立解释变量和直觉，补成公式解释组件。
- 概念底座把多个关键术语堆在同一段，拆段或拆小标题。
- 关键英文术语没有“英译中 / 怎么理解”，补上。
- 抽象概念仍然只靠长文字说明，补 SVG 动作图或关系图。
- 稍微复杂的机制、对照、公式或调度逻辑没有 SVG 图解，补图。
- 研究目的只有“提升性能/提高效率”，重写到“对象 / 瓶颈 / 收益”。
- 没有旧瓶颈到关键动作的因果链，重写。
- 把资料包、年份或论文名气当主体，重写。
- 可见标题出现内部工作词，改成读者能懂的标题。
